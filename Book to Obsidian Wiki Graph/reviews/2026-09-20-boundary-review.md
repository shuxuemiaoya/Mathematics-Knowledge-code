# Agent 边界审查与修复

本轮接续 [GitHub 对照审查](2026-09-17-agent-pipeline-review.md) 和 [第一轮修复](2026-09-20-pipeline-fixes.md)，检查概念插链、中断恢复、并发编辑以及已有书库兼容性。结论：又发现并修复了几类可复现的实现缺陷；混合书库需要明确的产物所有权，不能直接按新生成书籍整体处理。当前结果不等于已经完成真实整本教材的端到端验收。

## 已复现并修复的问题

| 问题 | 复现结果 | 本轮修复 |
| --- | --- | --- |
| 相对链接分支不可用 | profile 设置 `note_mode: relative` 后，概念插链报错 | 按每篇来源笔记和概念笔记的位置分别计算相对目标 |
| 同段多概念相互破坏锚点 | 第一个链接改变原句，第二个概念无法再匹配完整原句 | 在不可变原文上计算全部替换范围，逆序应用；重叠范围在写入前拒绝 |
| 计划后的人工修改被覆盖 | 在概念规划和提交之间修改来源笔记，旧实现仍写回旧计划 | 固定首次读取的哈希；概念、经审查正文修复、格式化和元数据在提交前核验原始读集合，并逐个复核目标 |
| 恢复未保护复用概念 | 已有概念不在写集合中，事务准备后修改它仍可能继续发布 | 只读复用目标也进入恢复保护集合；复用等价检查同时比较正文及原有链接目标 |
| 活跃执行可以被提前完成或失效 | 当前 PID 仍存活时可以完成阶段；上游失效也可能先抹掉下游执行记录 | begin、complete、resume 在变更状态前统一检查所有执行记录，包含 failed 状态；进程仍活跃或状态不明时阻止操作 |
| 同一日志可被同时恢复 | 同一发布计划缺少执行互斥 | 概念和修复事务增加操作系统文件锁；恢复时拒绝被重定向的路径，逐文件重新检查 |
| 全目录扫描包含别的模块产物 | formatter 和 metadata 会扫描书目录中全部 Markdown | 新增共享范围校验：依据当前 profile 的覆盖清单和概念清单确定管理范围；缺文件或出现未归属文件时，在整批写入前停止 |

Windows 进程检查另做了平台修正：`os.kill(pid, 0)` 不能作为跨平台的无副作用存活探针，Python 文档说明 Windows 上非控制事件信号使用终止进程机制。Windows 分支现在通过进程句柄和零超时等待查询状态。[Python 文档](https://docs.python.org/3.13/library/os.html#os.kill)、[OpenProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess)、[WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject)。本轮只验证了平台分派，不是原生 Windows 验收。

主要实现位于 [事务模块](../lib/book_graph_transaction.py)、[范围模块](../lib/book_graph_scope.py)、[概念应用](../skills/book-graph-concepts/scripts/apply_concept_candidates.py) 和 [协调器](../skills/book-to-obsidian-wiki-graph/scripts/pipeline_runtime.py)。格式化、元数据及经审查修复共同采用原始读集合保护。接口说明已更新到 [WORKFLOW-INTEGRITY.md](../WORKFLOW-INTEGRITY.md) 及各阶段 README。

## 真实书库的只读检查

检查目录为 `/Users/oven/Documents/ovenmathmap/高中/课堂同步/智慧中小学/必修第一册`。读取 **1,316** 篇 Markdown，仅在内存调用格式化和保真检查，没有写入书库。

- **770** 篇通过全部 formatter 不变量。
- **0** 篇触发正文顺序与内容保真失败。
- **546** 篇只触发 `quoted_body_callout_continuity`，全部位于 `answers` 目录。

这些独立答案笔记带有答案模块的来源元数据和嵌套 callout，遵循另一套格式合同。这个结果说明当前 agent 的 callout 规则与该模块不兼容，不能据此判定答案损坏，更不能为了使检查通过而批量重写它们。新范围校验会阻止未经清单归属的文件进入格式化和元数据批处理；它不会自动迁移或接纳混合书库。

详细计数与样例见 [只读检查记录](2026-09-20-existing-vault-readonly-check.json)。这不是全流程审计，也没有检验每篇内容与 PDF 原书的识别一致性。

## 尚存边界与后续优先级

1. **协调器启动仍有狭窄的崩溃窗口。** 代码审查发现，`Popen` 启动子进程后、子 PID 持久化前，状态中仍是父 PID；若父进程恰在此时退出而子进程继续运行，后续恢复可能误判执行已结束。本轮没有做这一窗口的真实进程故障注入，也没有实现启动握手。下一步应由子进程确认登记后才开始工作，并为协调器状态变更加运行级互斥；当前发布日志锁只约束同一日志的发布者。
2. **人工编辑保护仍不是文件系统事务隔离。** 哈希复核与文件替换之间存在很小的时间窗口，外部编辑器也不遵循本 agent 的日志锁。批处理中断可能留下部分已写文件；不要在阶段审计通过前把它作为完成产物。
3. **旧清单必须经过迁移审查。** 缺少来源、所有权或内容证据的旧清单不应从当前笔记直接补哈希。已有完整原文原子应保留并审查归属；混合答案模块需要独立范围合同。
4. **书籍知识图谱的语义质量仍需单独验收。** GitHub 对照提出的独立关系证据层、先修关系审核、概念召回评估，以及基于已审计原文的 skill 检索入口，仍属于后续能力建设。本轮修复的是执行正确性与保真门禁，没有把 Canvas 或文件数量当作知识质量证明。

本轮未改动实际 Obsidian 书库，未提交 Git。原始审查与第一轮测试记录保留其当时结果，本文件记录本轮增量。
